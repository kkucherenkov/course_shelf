## Goal

Re-import one course without re-reading the whole library.

## Why

Today the only entry point is `POST /api/v1/libraries/{id}/scans`, and
`RunScanCommand` takes `libraryId` alone. On the maintainer's library a full
scan is **over an hour** — 474 GB, and one `ffprobe` per video file. After
fixing E32-F01-S01, 37 courses need re-importing; without this card each
attempt costs a full scan.

The walk itself is cheap — it is a directory listing. The cost is `ffprobe`, so
scoping the *processing* to one folder is most of the win even if the walk stays
whole.

## The trap — read before writing any code

The scan treats orphan detection as "everything not seen during this walk is
gone": a lesson whose `videoPath` is absent from `seenVideoPaths` when the walk
ends has vanished from disk, and its `Transcript` rows are cleaned up. The
comment at `run-scan.handler.ts:244-247` states it.

That logic assumes **the walk is always complete**. A scoped rescan that fills
`seenVideoPaths` with one folder's files makes every other course look deleted.

So the substance of this card is not "add a filter" — it is making orphan
cleanup aware of the scan's scope. Getting this wrong destroys more than the
feature repairs.

## Acceptance

- `POST /api/v1/courses/{id}/rescan` — admin-only, 202 like the library scan
- `RunScanCommand` carries an optional scope; the library-wide path is
  unchanged and still the default
- Orphan cleanup only considers lessons **within the scanned scope**; a scoped
  rescan never touches another course's rows
- The scan record and its realtime events name the scope, so the UI can say
  "rescanning <course>" rather than implying a full scan
- A rescan button on the course page, next to the metadata editor, admin-only
- Strings via `t()` in `en` and `ru`; `pnpm check:i18n` green
