## Goal

Pressing **Rescan** on a course makes that course match the disk.

## Why

`POST /api/v1/courses/{id}/rescan` shipped and could not repair the course it
was pointed at. `run-scan.handler.ts` skipped any course whose slug was already
in the database — 140 lines before the only `lessonRepo.save`, so for a course
that already existed no lesson was ever written: not a missing one, not a
corrected position. All a rescan could do was refresh sidecars and thumbnails
for lessons that already existed.

The maintainer's library had imported with **1577 of 5984 lessons missing
(26 %)** and no rescan could fix any of it; the catalogue had to be wiped with
raw SQL and re-imported.

The skip itself is sound and stays: a library-wide scan must not clobber a
title, poster or tag list the user edited. What was missing is that naming
**one** course is a different request. Scope is therefore the force signal —
no new flag, no new endpoint.

## The trap — read before writing any code

Four of them, all about identity:

1. `LessonProgress`, `Bookmark`, `Note` and `Transcript` reference `lessonId`
   as a plain `String` with **no foreign key** (verified against the live
   database). Re-importing a lesson with a fresh id orphans all four silently,
   with nothing in the schema left to collect them. Reconcile by `videoPath`
   and reuse the id.
2. `Lesson.section` is `onDelete: Cascade`. Rebuilding the aggregate with fresh
   `nanoid()` section ids and saving it drops every lesson of the course — that
   was #317. Reuse a section's id when its title survives.
3. Lessons are saved one at a time, so inserting a missing lesson mid-section
   walks the later lessons onto positions their neighbours still hold — the
   `(sectionId, position)` unique violation E32-F01-S01 traced lesson loss to.
   The positive range has to be emptied before the new order is written.
4. If the course's folder is gone from disk, the walk sees no files and **every**
   lesson looks vanished. Deleting then takes the whole course's learning data
   with it.

## Acceptance

- A scoped rescan re-derives sections, lesson order and lesson rows from disk;
  a library-wide scan keeps the v1 skip
- Lessons still on disk keep their id; sections keep theirs when the title matches
- Course metadata (title, slug, description, poster, level, language, rating,
  instructors, studios, tags) is never re-derived — `course.json` linking runs
  on first import only
- Positions after a resync are exactly `1..n` within each section
- A lesson whose video is gone is deleted with its transcript, cues, progress,
  bookmarks and notes — but only when the folder was re-read successfully
- Another course in the same library is untouched
- No schema change: the missing foreign keys stay missing, deliberately

## Tests

Handler: file count equals lesson count after a resync; positions are `1..n`
per section; an existing lesson keeps its id; a user-renamed title survives; a
vanished lesson is removed with its transcript and learning rows; nothing is
deleted when the folder itself is gone; another course is untouched; a
library-wide scan still skips a course it already imported. Domain:
`Course.replaceSections`. Adapter: `removeMany` deletes child-first in one
transaction, `parkPositionsForResync` shifts in one statement.

The scan handler's fake `LessonRepository` now enforces
`@@unique([sectionId, position])` like the real one — the old fake accepted two
lessons on one position, which is how a test named "imports the named course"
passed while importing nothing.

## Notes

- Scope is the force signal. A separate `force` flag would have to be set by
  the only button that can send it, on the only page where it makes sense —
  a flag with exactly one value is not a choice.
- Deleting a vanished lesson's progress and bookmarks is implicit in a rescan,
  not gated behind a confirmation: the row is only removed once the folder has
  been re-read successfully, so the video really is gone, and "the course
  should match the disk" is the whole premise of the button.
- `course.json` is treated as the *first import's* metadata source. After that
  the course row belongs to whoever edited it through the API, so re-linking is
  skipped on a resync. A user who wants `course.json` re-applied has no path
  today — filed rather than guessed at.
