# 0010 — The Claude Design bundle is the design source; `tokens.json` generates all three platforms

- **Status:** accepted
- **Date:** 2026-08-29
- **Deciders:** @kkucherenkov
- **Tags:** design-system, frontend, mobile

> Recorded retroactively. Established in
> [E00-F01-S01](../roadmap/tasks/E00-F01-S01.md) and
> [E03-F01-S01](../roadmap/tasks/E03-F01-S01.md).

## Context

The same visual language has to appear in a Vue component library, a Flutter
component library, and a Nuxt app. Hand-maintaining a colour scale in three
languages guarantees drift, and the drift is invisible until someone puts two
screens side by side.

The design itself was produced in Claude Design as 16 project prototypes plus a
shared foundation, and lands in `docs/design/` as JSX prototypes, HTML
bootstraps, and one `shared/tokens.json`.

## Decision

Two rules, one for the design and one for the tokens.

**The bundle is a visual reference, not import-time source.** The JSX prototypes
in `docs/design/cs-*/` are never bundled into `apps/web`; they document state
matrices, layout, copy and token usage. When a story or a page is implemented,
the corresponding prototype is the spec.

**`docs/design/shared/tokens.json` is the single token source**, read directly by
`@app/design-tokens` (`src/load.ts`) and emitted to five generated files:

| Target | Path |
| --- | --- |
| web CSS | `apps/web/app/assets/css/tokens.generated.css` |
| ui CSS (Storybook) | `packages/ui/src/tokens.generated.css` |
| web TypeScript | `apps/web/app/design-tokens.generated.ts` |
| ui TypeScript (Storybook) | `packages/ui/src/design-tokens.generated.ts` |
| mobile Dart | `packages/ui_flutter/lib/src/theme/tokens.g.dart` |

Every one carries an `AUTO-GENERATED by @app/design-tokens — do not edit by
hand` banner.

## Consequences

### Positive

- A colour or spacing change is one edit to `tokens.json` plus
  `pnpm design:build`, and it reaches Vue, Flutter and the app together.
- Reading the bundle directly means there is no second copy of `tokens.json` in
  the repo to drift from the first — the design hand-off _is_ the input.
- `pnpm design:audit` can compare the implemented inventory against the bundle
  and report what has not been built.

### Negative

- Generated files are committed, so a stale regeneration is possible; only the
  Dart output is protected by a CI check (via the goldens), and there is no
  drift guard for the CSS/TS outputs equivalent to the codegen one.
- Tokens are gitignored in `apps/web`, so `pnpm design:build` is a prerequisite
  for several builds — including the web Docker image, which fails to resolve
  `tokens.generated.css` without it. That step is easy to forget and is
  duplicated across five CI jobs.
- The prototypes are JSX that nothing compiles or tests, so they can rot against
  the implementation with no signal.

### Neutral

- `packages/ui` gets its own copies of the CSS and TS so Storybook renders
  without depending on `apps/web`, and the Dart output lives in
  `packages/ui_flutter` (the design system) rather than `apps/mobile` (the
  consumer).

## Alternatives considered

### Option A — hand-maintain tokens per platform

Rejected: three sources of truth for one palette is the drift problem stated
plainly.

### Option B — Style Dictionary

The obvious off-the-shelf choice. Rejected because the pipeline needed is small
— load, normalise, emit three formats — and a custom `packages/design-tokens`
(five source files) is less than the configuration Style Dictionary would need
to emit a Flutter `ThemeData` factory.

### Option C — copy `tokens.json` into `packages/design-tokens`

Explicitly rejected, and the reason is recorded on
[E03-F01-S01](../roadmap/tasks/E03-F01-S01.md): a copy is a second thing to keep
in sync with the design hand-off, for no benefit over reading the bundle.
