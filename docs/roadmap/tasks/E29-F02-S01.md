## Goal

Check whether a lesson actually landed, using the words it actually used.

## Acceptance

- Questions generated from a lesson's cues, each carrying the timestamp it came from
- Generation is a reviewable proposal, not an automatic write — the `IdentifyTask` propose/apply/discard pattern already models this
- The engine choice is explicit and documented, including whether any content leaves the machine
- Generation is triggered on demand only (`POST /lessons/{id}/quizzes`,
  `POST /courses/{id}/quizzes`) — never on a scan or an import
- Model weights (whisper's AND llama's) are manageable from one admin surface:
  `GET /admin/model-weights` (list, both engines, with size) and
  `DELETE /admin/model-weights/{filename}` — added as an extension of this
  card's scope, per the maintainer's clarification during implementation
  (see PR body)

- Stage B and deliberately last in F02: a self-hosted personal instance sending its course audio or transcripts to a third party is a decision the owner makes, not one the roadmap makes for them.
- Design settled across 9 maintainer clarifications during implementation —
  full trace in the PR body. Highlights: local llama.cpp (`llama-completion`
  binary, not the originally-assumed `llama-cli`), two on-demand routes
  (lesson/course, no library-wide), model chosen per request from a shared
  weights volume with the admin list/delete surface this required, a
  windowing + ephemeral ASR-cleanup pass ahead of generation, and no
  persisted "run" record — the `Quiz` proposal itself is the run record.
