## Goal

Web ships `en`/`ru`; mobile ships `en`/`ru`/`uk`/`el`, two of them machine-written and unreviewed. The mismatch is recorded as a defect, which it is not — it is an unmade decision.

## Acceptance

- One of: drop `uk`/`el` from mobile, or keep them and stop calling the difference a limitation
- `pnpm check:i18n` reflects whatever is decided
- Both Known-limits rows removed or rewritten to state the actual position

## Notes

- Shipping an unreviewed machine translation is a defensible choice; calling it a defect and leaving it in place for months is not.
- **Decided: dropped, not kept.** `uk` and `el` are gone from mobile; both apps
  now ship `en` and `ru`. An unreviewed machine translation shipped as a
  supported locale is a promise the project cannot keep — a language picker
  entry says "we speak this", and nobody here can confirm the strings are right,
  let alone fix a report about them. Keeping them would have meant either
  paying for review or leaving the promise standing; dropping costs nothing and
  is true. Nothing prevents a reviewed locale being added back later.
- Removed: all 18 `*_uk.i18n.json` / `*_el.i18n.json` files, the `localeEl` /
  `localeUk` keys (dead — nothing read them), and the two picker entries in
  `settings_screen.dart`. `supportedLocales` needed no edit: it is
  `AppLocaleUtils.supportedLocales`, derived by slang from the files that exist.
  Locale is not persisted (`LocaleSettings.useDeviceLocale()` on every launch),
  so no user is stranded on a locale that no longer exists.
- `pnpm check:i18n` needed no change — it enumerates locales from the filenames.
  It now reports `mobile: 2 locale(s) × 293 key(s)`, matching web's 2.
