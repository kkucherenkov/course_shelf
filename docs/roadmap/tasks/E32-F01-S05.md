# E32-F01-S05 — A course title with no Latin letters must not delete the course

**Status:** ✅ Done
**Stage:** A
**Owner:** claude
**Estimated duration:** 0.5 day

**Epic:** E32 — Import correctness
**Feature:** F01 — Scan fidelity

## Dependencies

- [E32-F01-S04](./E32-F01-S04.md) — same file. Independent defect; landed after
  it so the two diffs in `run-scan.handler.ts` do not fight.

## Goal

A course whose title contains no Latin letters imports under a slug derived
from that title, and two courses whose titles legitimately reduce to the same
slug both import with the collision recorded as a `ScanError`.

## Why

The fourth independent way this scanner lost lessons, and half of all remaining
loss after E32-F01-S04.

`toSlug` in `run-scan.handler.ts` stripped `[^a-z0-9]`. A Cyrillic title became
a run of hyphens, the hyphens were trimmed, the result was empty, and the
function fell back to the literal `'untitled'` — so **every Latin-free title
produced the same slug.** `existingSlugSet.has(slug)` then treated the second
such course as already-imported and `continue`d, silently, with no `ScanError`.

Measured on the maintainer's library after a clean 1.2.0 import:

| | |
| --- | --- |
| Latin-free course folders | eight; **one** imported, **seven** dropped |
| Lessons lost | **253**, with no error recorded anywhere |
| Scan vs database | `coursesDiscovered: 68` against 61 rows, and nothing reconciles the two |
| Database | exactly one row held `slug = 'untitled'` |

The same strip lived in `slugify()` (`domain/shared-vo/entity-slug.ts`), used
for instructors, studios and tags. There it did not fall back — it **threw**
`EntitySlugInvalidError`, so a Russian instructor name could not be recorded at
all. The OpenAPI `displayName` pattern `[A-Za-z0-9]` (added by #321 to stop the
contract promising input the domain refused) rejected it one layer earlier.

## The fix

**Slugs become Unicode**, not transliterated: `Графы и комбинаторика` →
`графы-и-комбинаторика`. A course is never addressed by slug — every route is
`/api/v1/courses/{id}` with a cuid — so the slug's only jobs are uniqueness
within a library and human recognition, and for a Russian-speaking owner a
Cyrillic slug does both better than `grafy-i-kombinatorika`. It is also
script-neutral: a Chinese or Greek library works the same day, which no
transliteration table gives without a dependency per script.

Three parts:

1. **Charset.** `[\p{Ll}\p{Lo}\p{Lm}\p{N}]` at the ends, plus `\p{M}` inside.
   Uppercase is excluded deliberately — Postgres unique indexes are
   case-sensitive, so `Графы` and `графы` would be two rows. `\p{M}` is inside
   only, so Indic and Thai vowel signs survive instead of collapsing to hyphens.
2. **NFC before slugging.** `й` arrives either precomposed (U+0439) or
   decomposed (U+0438 + U+0306); macOS hands out the decomposed form for
   filenames. Un-normalised, the two encodings of one visual title produce two
   slugs that `@@unique([libraryId, slug])` cannot see as the same — which is
   the whole reason the constraint would still let duplicates through.
3. **A collision is no longer a silent skip.** "Slug is taken" and "this folder
   is already imported" were the same question only while one title could
   produce one slug. The walk now resolves the taken slug's owning folder from
   its lessons' `videoPath`, and a slug held by a *different* folder makes the
   loser take a deterministic folder-derived suffix (`sha256(folder)[0..8]`) and
   import, with a `course-slug-collision` `ScanError`. Folder-derived, not a
   counter: a counter renumbers when a sibling folder appears or disappears, and
   the next rescan would import a second copy of a course it already had.

`toSlug` now delegates to `slugify` and only supplies the scan's own
`'untitled'` fallback, so the derivation exists once. `CourseSlug`'s regex was
a second verbatim copy of `EntitySlug`'s; it now imports it.

## Verified, not assumed

`\p{L}` requires the `u` flag — without it the escape still compiles and then
matches **nothing**, so a spec pattern built from it would reject every value
instead of fixing the bug. JSON Schema `pattern` is ECMA-262 and validators
differ on whether they compile with `u`.

`express-openapi-validator@5.6.2` resolves to `ajv@8.18.0` (via `ajv/dist/2020`
for this OpenAPI 3.1 document) and never sets `unicodeRegExp`, whose ajv default
is `true`. Compiling the pattern through `factoryAjv` and testing it confirms
Cyrillic, Han, Greek, Japanese and Devanagari all match, and that uppercase,
leading/trailing hyphens, spaces and 101 characters still do not. Setting
`unicodeRegExp: false` makes the same pattern match nothing at all, which is the
trap. An e2e test now asserts this through the real middleware.

## Acceptance

- A Latin-free title produces a slug derived from that title, not `'untitled'`
- Two different Latin-free titles produce two different slugs and both courses
  import
- The two encodings of one visual title produce one slug
- A genuine collision records a `ScanError` and still imports both courses, with
  the same discriminated slug on every subsequent scan
- Accented Latin does not regress (`Café` → `café`)
- The spec pattern and the domain regex agree, asserted by a test that reads the
  pattern out of `openapi.yaml`
- A Cyrillic instructor `displayName` is accepted by the running validator

## Spec diff

`CourseSlug.pattern`, `EntitySlug.pattern`, and the `displayName.pattern` of
`UpsertInstructorRequest` / `UpsertStudioRequest` / `UpsertTagRequest`
(`[A-Za-z0-9]` → `[\p{L}\p{N}]`). No route, schema or type changed.

## Tests

`entity-slug.spec.ts`: the anti-drift gate reading both patterns out of
`openapi.yaml`; a test that fails if `SLUG_RE` loses its `u` flag; Unicode
slugify cases per script; NFC equivalence for both encodings; the astral
truncation guard.

`run-scan.handler.spec.ts`: eight Cyrillic folders import as eight courses with
eight distinct slugs and no `'untitled'`; a rescan of that library is a no-op; a
collision imports both and records one `course-slug-collision`; the discriminated
slug is stable across scans; the NFC/NFD folder pair collides rather than
silently duplicating.

`http-contract.e2e-spec.ts`: the running validator's compiled `EntitySlug`
pattern accepts seven scripts and still rejects uppercase, hyphens at the edges,
spaces, underscores and over-length — plus the `displayName` search.

## Notes

- **Existing deployments.** No migration ships. A row with `slug = 'untitled'`
  is a valid slug and keeps working; the courses that were *dropped* have no row
  to migrate, so the repair is a rescan, which now imports them. A deployment
  that wants the cosmetic slug as well can delete the `untitled` course and
  rescan — a scoped rescan will not change it, because a resync deliberately
  never re-derives the course row. Instructor, studio and tag rows that were
  never written are created by the same rescan.
- `\p{M}` inside the slug is broader than the measured defect needed (Cyrillic
  and Han need no marks). Included because omitting it recreates this exact bug
  for Devanagari and Thai, at the cost of one class member.
