# E32-F01-S01 — Lesson position must be unique within its section

**Status:** ✅ Done
**Stage:** A
**Owner:** claude
**Estimated duration:** 1 day

**Epic:** E32 — Import correctness
**Feature:** F01 — Scan fidelity

## Dependencies

- None.

## Goal

Stop the scanner from silently dropping lessons whose computed position collides.

## The measurement that opened this

Taken from the maintainer's real 474 GB library on the first production import,
2026-09-13 — counted by joining video files on disk against `lesson` rows,
matched on `videoPath` rather than on titles:

| | |
| --- | --- |
| Video files on disk | 5720 |
| Lessons in the database | 4407 |
| **Lost** | **1313 (23 %)** |
| Courses imported exactly | 24 |
| Courses with losses | **37** |

Three shapes, all measured:

- **Flat, digits as a suffix** — `Основы Domain Driven Design`,
  `lesson1.mp4` … `lesson23.mp4`. `stem-match`'s prefix patterns are anchored
  `^`, so no ordinal parses, every file gets position 1, and **one** lesson
  survives.
- **Flat, composite prefixes** — `Основы Golang`, 128 files named `10.1.`,
  `10.2.`, `11.1.`. The ordinal is the *second* number, so it repeats in every
  chapter, and a flat layout puts them all in one synthetic `Lessons` section:
  exactly 16 lessons over 16 distinct positions.
- **Nested is not immune** — `Udemy — The Ultimate Guide to Game Development
  with Unity` lost 58 of 522, `Udemy — JavaScript The Complete Guide 2025` lost
  42 of 540. Ordinals repeat inside sections too.

`stem-match` is **not** the culprit: run over `lesson1` … `lesson23` it returns
23 distinct canonical stems, so grouping is correct. The loss happens at
position assignment — `run-scan.handler.ts:645` and `:654`, both
`lessonPosition = parsed.ordinal ?? 1`.

**Correction (live NAS run, same day):** the loss is not a silent overwrite —
`schema.prisma` already carries `@@unique([sectionId, position])`, and the
backend log shows it firing: `Unique constraint failed on the fields:
(sectionId, position)` on `prisma.lesson.upsert()`. Every lost lesson threw.
It looked silent to the operator only because the resulting `ScanError` lives
on the `Scan` aggregate and is not persisted until `scanRepo.save()` runs at
the end of the walk — and a second, separate defect (next paragraph) made
that final save throw too, so the whole batch of accumulated errors was rolled
back with it. The fix is still "make position genuinely unique," not "touch
the constraint" — the constraint is the invariant doing its job.

**Second defect, folded into this card (tuxedo 118):** `DiscoveredFile.size`
and `Lesson.sizeBytes` were both `Int` (int4, caps at 2147483647 bytes /
~2GB). The library holds a 3129930702-byte file; `prisma.discoveredFile
.createMany()` threw `"Value out of range for the type"` inside the same
transaction that also writes `scan_error_record` rows, rolling both back. The
scan row stayed `status=running` with `finishedAt=NULL` forever — no failed
state, no reason recorded, indistinguishable from a slow scan.

## Acceptance

- Two lessons in the same section can never share a position; the scan either
  assigns distinct positions or fails loudly
- When no ordinal parses from the filename, position comes from walk order, and
  that order is stable across rescans of unchanged content
- A collision that cannot be resolved is recorded as a `ScanError`, never a
  silent overwrite
- A flat course folder imports **every** video file it contains
- Re-importing the three measured courses yields 23, 128 and 49 lessons
- `DiscoveredFile.size` and `Lesson.sizeBytes` are `BigInt` — a file past
  Int32's ~2GB cap no longer throws `"Value out of range"`
- A crash anywhere in the walk marks the scan `failed` and records the cause
  as a normal `ScanError` — never leaves the row stuck at `status=running`
  with no trace

## Schema impact

yes — `DiscoveredFile.size` and `Lesson.sizeBytes`: `Int` → `BigInt`
(migration `20260913150000_lesson_discovered_file_bigint_size`). Domain and
DTO shapes are unchanged: the Prisma adapter layer converts `bigint` → `number`
on read (`Number()`, safe to `Number.MAX_SAFE_INTEGER` ≈ 9 PB) and Prisma
accepts a plain `number` on write for a `BigInt` column, so no other layer
(query handlers, controllers, `@app/specs` DTOs) needed a type change.

## Design impact

no

## Tests

Handler tests over each measured shape: flat with suffix digits, flat with
composite `N.M` prefixes, nested with ordinals repeating across sections, and a
mixed folder. Each asserts the lesson **count** matches the file count — the
assertion that would have caught this. Plus a test that a genuine collision
surfaces as a `ScanError`, and a BigInt round-trip test (repository level) plus
a full-walk smoke test for a file past Int32 range.

## Notes

- Opened from `tuxedo` 116.
- The loss looked silent operationally, but the DB constraint was firing the
  whole time (see the correction above) — the count-asserting tests are still
  the part that keeps it fixed, independent of which layer raises the error.
- Position rule chosen: `assignLessonPositions()`
  (`domain/scan/lesson-position.ts`) ranks every lesson within a section by a
  sort key — the parsed ordinal, composed with `sectionOrdinal` for composite
  `N.M` filenames so chapter numbering never collides on the repeated lesson
  number — falling back to the full `videoPath` when no ordinal parses. The
  emitted position is always the 1-based rank, never the sort key itself,
  because `lesson.position` is rendered directly as the lesson number in the
  UI (`CourseSectionsList.vue`) and must stay a small sequential integer.
  Ranking also makes collisions structurally impossible: N lessons always
  produce N distinct positions.
- `folder-name.parser.ts` gained a trailing-digit tier (`lesson23` → ordinal
  23) so the flat suffix-digit shape gets its natural numeric order instead of
  falling back to alphabetical (`lesson1, lesson10, lesson11, …, lesson2`).
- Ships tuxedo 118 (BigInt widening) in the same PR — same handler, same root
  cause class (a real-library measurement nobody had run against before), and
  a rescan feature is pointless while one oversized file can still kill a run.
- Completed: 2026-09-13
- Result: [PR #463](https://github.com/kkucherenkov/course_shelf/pull/463)
- Found but out of scope: `stemMatch()` keys off the file **basename** only,
  ignoring the containing folder. A course whose sections repeat an identical
  lesson filename (e.g. every section literally has a `1. Introduction.mp4`)
  would collapse those into one stem group and lose all but the last. Not
  observed in the measured library and not part of either correction above —
  worth a follow-up if a future measurement shows it.
