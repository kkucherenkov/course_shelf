# E32-F01-S04 — Two videos may share a filename in different section folders

**Status:** ✅ Done
**Stage:** A
**Owner:** claude
**Estimated duration:** 0.5 day

**Epic:** E32 — Import correctness
**Feature:** F01 — Scan fidelity

## Dependencies

- [E32-F01-S03](./E32-F01-S03.md) — same file, same PR. A resync is what puts
  the lost lessons back, so the two fixes are only useful together.

## Goal

A course whose sections each contain a `video.mp4` imports one lesson per
section, not one lesson in total.

## Why

The third independent way this scanner lost lessons, found live and measured in
1.2.0, unrelated to the position bug (E32-F01-S01) and to the rescan skip
(E32-F01-S03).

`stemGroups` in `run-scan.handler.ts` is built **once per course** and was keyed
by `canonicalStem` alone. `stemMatch` reads the **basename** only — by contract,
stated in `stem-match.ts` — so two videos in different section folders that
share a filename landed on one key, and `group.video = { … }` silently
overwrote the earlier one. No `ScanError`, no warning: the lesson simply never
existed.

Measured on the maintainer's library:

| | |
| --- | --- |
| `[Фоксфорд] Шахматы начальный уровень 3-7 классы` | 31 videos, all named `video.mp4`, one per numbered section folder. All 31 sections created; **1 lesson imported**. |
| Whole library | **296 videos across 18 courses**, ~5 % of 5984. Worst cases: 40 lost of 49, 30 lost of 31 (twice), 42 lost of 540. |

## The fix

Key the group by `(directory, canonical stem)` instead of the stem alone. The
handler owns the key; `stem-match.ts`'s own contract is fine and unchanged — it
is documented as basename-only and other callers rely on that.

A sidecar is by definition a **sibling** of its video, so scoping the key to the
directory cannot break video/sidecar pairing, which is the only thing sharing a
key was ever for.

## Acceptance

- A course with identically-named videos in sibling section folders imports one
  lesson per folder
- Sidecars still attach to the video in their own folder, never to a namesake
  elsewhere in the course, and produce no `unsupported-extension` errors
- A rescan of an already-collapsed course back-fills the missing lessons and
  leaves the one that survived with its id

## Tests

Three, in `run-scan.handler.spec.ts`: one lesson per folder for a four-folder
fixture (lesson count equals file count, the shape E32-F01-S01 established);
sidecars pair within their own directory; a scoped rescan back-fills a course

alone — all three fail.

## Notes

- Sibling folders whose names reduce to the **same label** still collapse into
  one `Section` (`sectionMap` is keyed by label, deliberately — see the comment
  there). That is a naming outcome, not lesson loss: after this fix both
  folders' lessons land in that one section at distinct positions. Left alone.
- Every lesson in such a course is titled `video`, because that is what the
  file is called. Inferring a title from the containing folder is a product
  decision, not a scanner fix.
