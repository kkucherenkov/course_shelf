## Goal

Re-import one course without re-reading the whole library.

## Why

Today the only entry point is `POST /api/v1/libraries/{id}/scans`, and
`RunScanCommand` takes `libraryId` alone. On the maintainer's library a full
scan is **over an hour** — 474 GB, and one `ffprobe` per video file. After
fixing E32-F01-S01, 37 courses need re-importing; without this card each
attempt costs a full scan.

The walk itself is cheap — it is a directory listing. The cost is `ffprobe`, so
scoping the *processing* to one folder is most of the win even if the walk stays
whole.

## The trap — read before writing any code

The scan treats orphan detection as "everything not seen during this walk is
gone": a lesson whose `videoPath` is absent from `seenVideoPaths` when the walk
ends has vanished from disk, and its `Transcript` rows are cleaned up. The
comment at `run-scan.handler.ts:244-247` states it.

That logic assumes **the walk is always complete**. A scoped rescan that fills
`seenVideoPaths` with one folder's files makes every other course look deleted.

So the substance of this card is not "add a filter" — it is making orphan
cleanup aware of the scan's scope. Getting this wrong destroys more than the
feature repairs.

## Acceptance

- `POST /api/v1/courses/{id}/rescan` — admin-only, 202 like the library scan
- `RunScanCommand` carries an optional scope; the library-wide path is
  unchanged and still the default
- Orphan cleanup only considers lessons **within the scanned scope**; a scoped
  rescan never touches another course's rows
- The scan record and its realtime events name the scope, so the UI can say
  "rescanning <course>" rather than implying a full scan
- A rescan button on the course page, next to the metadata editor, admin-only
- Strings via `t()` in `en` and `ru`; `pnpm check:i18n` green

## Notes

- Opened alongside E32-F01-S01 after the first production import lost 23 % of
  lessons; that fix is what makes this immediately useful.
- Deliberately one course, not an arbitrary selection: a single scope keeps the
  cleanup rule simple to state and to test.
- `RunScanCommand.libraryId` became `string | undefined` with a new optional
  `scope: { courseId }` (both are on the same class — no discriminated union —
  to keep every existing call site and test constructing
  `new RunScanCommand(libraryId, actorUserId)` unchanged). The handler
  resolves the library from the course when scoped; `POST /courses/{id}/rescan`
  never has a libraryId to give it.
- Course stores no on-disk folder path, so the scoped folder is derived from
  one of the course's already-persisted lessons' `videoPath`. A course with
  zero lessons can't be scoped — recorded as `course-scope-unresolvable`, and
  nothing is treated as orphaned in that case (see the trap below).
- The trap's actual fix: `existingLessonByVideoPath` — the map orphan cleanup
  reads at the end of the walk — is built from **only the scoped course's own
  lessons** (one query) instead of every course in the library (N+1 queries).
  Scoping that one map scopes both the mid-walk sidecar-refresh path and the
  end-of-walk cleanup for free; no separate filter was needed once the
  indexing itself was scoped.

- Result: [PR #465](https://github.com/kkucherenkov/course_shelf/pull/465) (stacks on [PR #463](https://github.com/kkucherenkov/course_shelf/pull/463))
- Deliberate non-goal: a scoped rescan of a course that still has its slug
  persisted does not back-fill lessons that E32-F01-S01's bug already dropped
  — the existing v1 "skip on duplicate slug" idempotency is untouched by this
  card. There is no per-course delete yet (only library-level cascade delete)
  to clear a broken course before rescanning it fresh; tracked as a follow-up
  if the maintainer's 37 affected courses need it.
